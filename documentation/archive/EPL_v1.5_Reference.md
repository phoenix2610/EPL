## 1. Philosophy

EPL exists to solve the **vibe coder problem**.

When developers use AI to generate all their code, they lose the mental model. When the codebase grows and needs changes, they face a wall of logic they never understood. They trade speed for effectiveness — and pay the cost later.

EPL fixes the bridge. English is the language of context, and in EPL, that context *becomes* the syntax. The programmer's thought process is the source code.

```
Human thought → EPL → C Interpreter → Execution
                ↑
         You always stay here.
         You always understand what you wrote.
```

### The describe navigation system

This is EPL's most strategically important feature — and with v1.5, it becomes a real, runnable, measurable system.

In a 10,000 line codebase:

```
Python:   LLM reads 10,000 lines  →  ~12,000 tokens minimum
EPL:      LLM reads .EPD file     →  ~800 tokens
          identifies relevant section by line range
          reads those 300 lines   →  ~400 tokens
          Total: ~1,200 tokens    vs  12,000
```

The `describe` block is not a comment. It is a **semantic index entry** — structured, extractable, LLM-navigable. The `.EPD` file is the compiled form of every describe block in the program, paired with line ranges, types, and signatures. An LLM reads the `.EPD` to understand the entire program's intent without reading a single line of logic.

This is not philosophical. Starting v1.5, it is a file you can generate and measure.

### Token density

EPL's advantage over Python is not just fewer lines. It is **semantic token density** — more meaning per token consumed. Python has noise: `def`, `self`, `__init__`, `:`, type hints, decorators. Every EPL token is signal. This makes EPL 5-6x more efficient for LLM context consumption even at identical file sizes.

### Full stack vision

EPL is on a path to become a full-stack language — logic (`.EP`), frontend (`.EPF`), and data (`.EPDB`, planned for v1.10) all expressible in English. One language. One mental model. No context switching.

## 2. File Types

| Extension | Purpose | Produces |
|-----------|---------|---------|
| `.EP`     | Logic, computation, backend | Terminal execution |
| `.EPF`    | Frontend pages, charts, tables | `.html` files (live-bound) |
| `.EPDB`   | Data definitions, queries *(planned — v1.10)* | `.epdb` store |
| `.EPD`    | Semantic index — **read-only, generated** | LLM navigation layer |

The `.EPD` is never written by hand. It is always generated by:

```powershell
.\epl.exe --describe program.EP      # produces program.EPD
.\epl.exe --describe dashboard.EPF   # produces dashboard.EPD
```

### Live binding — `.epbind`

Every `.EPF` output is tracked in a `.epbind` file. Re-run the `.EPF` → HTML regenerates. The `.EP`/`.EPF` file is the source of truth. The HTML and `.EPD` are compiled artifacts.

## 3. Running EPL

### Building from source

```bash
gcc -Wall -std=c11 -o epl main.c lexer.c token.c ast.c parser.c interpreter.c repl.c codegen.c binding.c describe.c -lm
```

### Running files

```powershell
.\epl.exe program.EP           # logic execution
.\epl.exe dashboard.EPF        # generates HTML
```

### Debug and index flags

```powershell
.\epl.exe --tokens   program.EP    # show token stream
.\epl.exe --ast      program.EP    # show abstract syntax tree
.\epl.exe --describe program.EP    # generate program.EPD  ← v1.5
.\epl.exe --describe dashboard.EPF # generate dashboard.EPD
```

### REPL

```powershell
.\epl.exe
```

### Fix Windows terminal encoding

```powershell
chcp 65001
```

## 22. Frontend Pages — EPF *(v1.4)*

`.EPF` files generate self-contained HTML — Chart.js and CSS embedded inline, zero external dependencies.

### Structure

```epf
make page saved as "dashboard.html" styled as "dark"

    heading "My Dashboard"
    subheading "Subtitle"
    paragraph "Body text."
    divider

    section "Charts"
        make line chart for x axis as months and y axis as revenue titled "Revenue"
    !

    section "Data"
        make table from students titled "Students" with headers ["Name", "Score"]
    !

!
```

### Text elements

| Syntax              | Output       |
|---------------------|--------------|
| `heading "text"`    | `<h1>`       |
| `subheading "text"` | `<h2>`       |
| `label "text"`      | `<h4>`       |
| `paragraph "text"`  | `<p>`        |
| `bold "text"`       | `<strong>`   |
| `divider`           | `<hr>`       |
| `spacer`            | vertical gap |

### Layout

```epf
row
    make stat "Average" from average of scores
    make stat "Maximum" from maximum of scores
    make stat "Total"   from total of revenue as formatted
!
```

### Charts

```epf
make line chart for x axis as months and y axis as revenue titled "Revenue"
make bar chart for x axis as subjects and y axis as scores titled "Scores"
make pie chart from categories and values titled "Distribution"
```

### Tables and reports

```epf
make table from students titled "Records" with headers ["Name", "Score"]
make report from scores titled "Class Statistics"
```

### Themes and colors

```epf
# Named themes
styled as "light"
styled as "dark"
styled as "indigo"
styled as "emerald"
styled as "rose"

# Custom — any unknown string becomes a custom accent color
styled as "persian blue"     # lookup table → #1c39bb
styled as "hot pink"         # lookup table → hotpink
styled as "forest green"     # lookup table → forestgreen
styled as "#2ecc71"          # hex passthrough
styled as "coral"            # CSS name passthrough

# Explicit accent override on a named theme
styled as "dark" with color "#f59e0b"
```

Custom colors derive a full consistent palette automatically — background, surface, text, borders — from the single accent color. Zero new keywords. Zero new tokens. `THEME_CUSTOM` handles everything.

## 23. Semantic Index — EPD *(v1.5)*

The `.EPD` file is EPL's most important infrastructure feature. It is the **compiled semantic index** of any `.EP` or `.EPF` file — generated automatically, never written by hand.

### Generating

```powershell
.\epl.exe --describe grades.EP        # produces grades.EPD
.\epl.exe --describe dashboard.EPF    # produces dashboard.EPD
```

`--describe` parses the file, extracts all describe blocks and their targets, pairs each with its line range, and writes the `.EPD`. The program is **not executed** — only indexed.

### The .EPD format

```
EPD 1.0 — grades.EP
generated: 2026-05-03 14:22:11
─────────────────────────────────────────────

[program ]  line 1        grades.EP
  "Analyzes student scores — term reporting and pass/fail tracking"

[activity]  lines 7-9     add
  params: x, y
  "Returns the sum of x and y"

[activity]  lines 12-18   divide
  params: x, y
  "Divides x by y — validates y is not zero before dividing"

[data    ]  line 21       passed
  type: list
  "Filters scores at or above the pass threshold of 60"

[data    ]  line 24       failed
  type: list
  "Filters scores below the pass threshold of 60"

[block   ]  line 27
  "Displays grade summary — totals, averages, pass rate"

─────────────────────────────────────────────
entries: 6 total  |  2 activities  |  1 blocks  |  2 data
```

### Entry types

| Type       | What it indexes                                    |
|------------|----------------------------------------------------|
| `program`  | Top-level program describe — what the file does    |
| `activity` | A `to ... !` block — includes params, line range   |
| `data`     | A `set` with a describe — includes inferred type   |
| `block`    | A describe over any other logic block              |
| `page`     | A `make page` in `.EPF`                            |
| `section`  | A `section` in `.EPF`                              |

### How to write describe blocks for best EPD output

The describe block immediately before a node is paired with it:

```epl
describe add as "Returns the sum of x and y"
to add
    return x plus y
!
```

```epl
describe passed scores as "Students who scored 60 or above"
set passed as scores where score at least 60
```

```epl
describe main loop as "Menu-driven calculator — handles history and exit"
while running
    show menu
    ...
!
```

```epf
describe revenue chart as "Monthly revenue Jan-Jun — line chart, dark theme"
section "Revenue"
    make line chart for x axis as months and y axis as revenue titled "Revenue"
!
```

### The LLM workflow

**Without `.EPD` — LLM debugging a 500-line file:**
```
Read 500 lines → ~600 tokens → scan for relevant section
```

**With `.EPD` — same file:**
```
Read .EPD     → ~150 tokens → spot "divide, lines 12-18"
Read lines 12-18 only → ~30 tokens
Total: ~180 tokens   vs   600  →  3.3x more efficient
```

**At 10,000 lines:**
```
Read .EPD            → ~800 tokens
Read relevant 300 lines → ~400 tokens
Total: ~1,200 tokens vs ~12,000  →  10x more efficient
```

This is not just faster for the LLM. It is cheaper for the developer — fewer tokens consumed means lower API costs, faster responses, and more accurate answers because the LLM isn't drowning in irrelevant context.

### The describe checkpoint system

The `.EPD` is EPL's answer to the LLM context window problem. In a long coding session on a large codebase, the LLM eventually loses context — it forgets what functions do, what variables mean, what the overall architecture is.

In Python, recovering that context means re-reading the entire file.

In EPL, recovering context means reading the `.EPD`:

```
LLM context lost after 2 hours of work
→ read grades.EPD  (~150 tokens)
→ full program intent restored
→ continue exactly where you left off
```

The `.EPD` is a **semantic checkpoint** — a dense, structured summary that restores LLM context on any EPL codebase in under 1,000 tokens regardless of how large the source files are.

### .EPD for EPF files

Frontend files benefit from the semantic index too. A dashboard with 20 sections and 15 charts is just as opaque to an LLM as a complex logic file — without the index:

```
EPD 1.0 — dashboard.EPF
generated: 2026-05-03 14:22:11
─────────────────────────────────────────────

[program ]  line 1        dashboard.EPF
  "Grade and revenue dashboard — Term 2 2026 — dark theme"

[page    ]  lines 7-45    dashboard.html
  "Full grade dashboard — metrics, charts, table, report"

[section ]  lines 10-15   Key Metrics
  "KPIs — average score, top score, pass rate, distinctions"

[section ]  lines 17-21   Revenue
  "Monthly revenue trend — line chart Jan through Jun"

[section ]  lines 23-27   Subject Performance
  "Bar chart of scores across 5 subjects"

[section ]  lines 29-32   Student Records
  "Full student name/score table with headers"

─────────────────────────────────────────────
entries: 5 total  |  1 pages  |  4 sections
```

An LLM reading that `.EPD` knows exactly which section to modify for any change request — without reading a single line of HTML-generating EPF code.

### Parameter extraction

For activities, the `.EPD` auto-extracts parameters by walking the activity body and identifying classic parameter names (x, y, z, a, b, c, n, m, n1, n2, etc.):

```
[activity]  lines 4-8    calculate bmi
  params: x, y
  "Calculates BMI from weight (x) and height (y)"
```

No annotation required. The extractor finds them automatically.

### Type inference for data entries

For `set` nodes paired with describe, the `.EPD` infers the data type from the value expression:

```
[data    ]  line 22    scores
  type: list
  "Raw student scores for the current term"

[data    ]  line 24    network
  type: graph
  "Supply chain relationship map"

[data    ]  line 26    pass rate
  type: number
  "Percentage of students who scored 60 or above"
```

No type annotation required. The interpreter walks the AST node type to infer it.

## 25. Documentation — `describe`

`describe` is EPL's self-documenting layer. Unlike comments — which are ignored by compilers, skipped by developers, and only useful to LLMs if they read the whole file — `describe` blocks are first-class AST nodes. They survive the tokenizer and parser. They are extractable. They power the `.EPD` system.

```epl
describe program name as "What this program does overall"

describe activity name as "What this activity does, what it returns"
to activity name
    ...
!

describe variable name as "What this data represents, where it comes from"
set variable name as some value

describe block name as "What this section of logic is responsible for"
while some condition
    ...
!
```

### Rules for effective describe blocks

**Be specific about scope:**
```epl
# Weak — too vague
describe add as "Adds numbers"

# Strong — captures intent, params, edge cases
describe add as "Returns sum of x and y — used for running totals in history"
```

**Describe the why, not just the what:**
```epl
# Weak
describe divide as "Divides x by y"

# Strong
describe divide as "Divides x by y — validates y is not zero to prevent runtime error"
```

**Describe data with its source and purpose:**
```epl
# Weak
describe passed as "Passed students"

# Strong
describe passed as "Students who scored 60 or above — used for pass rate and average calculations"
```

**One describe per logical unit** — activity, major data variable, or logic block. Don't describe every line. Describe every *concept*.

!
